# Локальная админка СМУ-1 — инструкция владельца (H6)

Админка H6 предназначена для многолетней работы с контентом сайта на одном доверенном компьютере. Она запускается из локального checkout, слушает только `127.0.0.1` и не публикуется как рабочий backend в интернет.

Телефон и другой компьютер подключиться к ней не могут — это намеренная граница безопасности. Мобильные и узкие скриншоты в QA проверяют только адаптивность окна, масштаб браузера и клавиатурную доступность на том же компьютере; они не означают удалённый доступ. Если когда-нибудь понадобится редактирование с телефона, это будет отдельный проект с серверной авторизацией, TLS, резервным хранением и новой моделью угроз.

## Самое важное

В админке есть три разных состояния:

1. **Черновик в браузере** — изменения видны только в текущем браузере и ещё не записаны в файлы сайта.
2. **Сохранено на компьютере** — создана локальная восстановимая транзакция. Git и GitHub не вызываются, тестовый сайт не меняется.
3. **Опубликовано на тестовом сайте** — выбранные сохранённые транзакции прошли проверки и отдельную preview-публикацию.

Кнопка **«Сохранить на компьютере» никогда не публикует сайт**. Production/main в H6 недоступны.

## Первичная настройка

Эту часть выполняет Павел или другой ответственный разработчик на компьютере владельца:

```bash
npm ci
npm run admin:setup
```

Setup создаёт локальный файл `.env.admin.local` с именем пользователя, scrypt-хэшем пароля и случайным session secret. Открытый пароль в файле не хранится. Не используйте очевидный пароль и не пересылайте `.env.admin.local` по почте или в мессенджере.

Не добавляйте в этот файл `GITHUB_TOKEN` или `GITHUB_DEPLOY_TOKEN`. GitHub status для публичного репозитория читается анонимно; при rate limit и для явного Retry backend обращается к системному Git Credential Manager через `git credential fill`. Секрет остаётся в памяти backend и не передаётся браузеру. Обычный `git push` продолжает использовать настроенный Credential Manager либо SSH. Если старые token-поля уже были в `.env.admin.local`, launcher остановится с безопасной диагностикой; при полностью закрытой админке `npm run admin:setup -- --rotate` удалит их вместе с ротацией локальных credentials.

После setup проверьте запуск:

```bash
npm run admin
```

Админка должна сама открыть `http://127.0.0.1:4321/admin/`.

### Ярлык Windows

В репозитории уже есть безопасный launcher: `tools/admin-api/SMU1-Admin-Start.cmd`.

1. Найдите этот файл в Проводнике.
2. Нажмите правой кнопкой → **Отправить** → **Рабочий стол (создать ярлык)**.
3. Запускайте созданный ярлык двойным кликом.

Не копируйте сам `.cmd` на рабочий стол: он вычисляет корень проекта относительно своего штатного расположения. Если папку проекта перенесли, создайте ярлык заново.

Для остановки закройте окно launcher или нажмите `Ctrl+C` в нём. Не завершайте работу удалением файлов из `.admin-runtime`.

## Безопасность рабочего места

- Открывайте только точный адрес `http://127.0.0.1:4321/admin/`.
- Не меняйте host на `0.0.0.0`, не настраивайте port forwarding, туннель, публичный proxy или общий сетевой доступ.
- Не вставляйте секреты и конфиденциальные документы в контент. Preview имеет `noindex`, но не является приватным сайтом.
- Работайте в одной основной вкладке. Защита от конфликтов есть, но один активный редактор остаётся самым понятным режимом.
- Не запускайте параллельно старые команды `npm run dev` и `npm run admin:api`: единый launcher запускает оба процесса сам.

Опубликованный маршрут `/admin/` на статическом сайте является только инструкцией запуска. Он не даёт доступ к локальным данным и не превращает GitHub Pages в admin backend.

## Обычный рабочий сценарий

1. Запустите ярлык и войдите под созданным логином.
2. Выберите раздел: страницы, каталог, услуги, объекты, вакансии, навигация или настройки.
3. Найдите запись через список и поиск.
4. Внесите изменения. Статус покажет несохранённый браузерный черновик.
5. Проверьте текст, видимость, связи, порядок и фотографии.
6. Нажмите **«Сохранить на компьютере»**. Дождитесь сообщения: «Сохранено на компьютере. Тестовый сайт не обновлялся».
7. Откройте из шапки записи точную локальную страницу и визуально проверьте сохранённую версию.
8. Рядом можно открыть точный маршрут этой же записи на тестовом сайте: при несохранённом черновике админка намеренно показывает последнюю сохранённую/опубликованную версию, а не выдаёт черновик за deployed-состояние.
9. Если обновление должно попасть в интернет, отдельно перейдите к preview-публикации, выберите нужные локальные сохранения и проверьте план.
9. Подтвердите публикацию один раз и дождитесь итогового зелёного статуса для точного commit SHA.

Новая запись создаётся скрытой. Сначала полностью заполните и проверьте её, затем отдельно включите публичную видимость и сохраните это изменение.

## Черновики, отмена и конфликты

Браузерный черновик сохраняется локально и может быть предложен к восстановлению после перезагрузки, закрытия вкладки или истечения сессии.

- **Отменить/Повторить** работают внутри текущего редактора и не переходят за последнюю загруженную или сохранённую границу.
- Выход из аккаунта не удаляет браузерные черновики.
- При сообщении «Запись изменилась в другой вкладке» слепая перезапись блокируется. Сравните версии, выберите значения полей и только затем снова сохраните.
- Если автоматическое сравнение невозможно, скачайте JSON черновика перед перезагрузкой актуальной записи.
- Не закрывайте конфликт принудительным обновлением страницы, пока не сохранили нужный черновик.

## История и восстановление

Раздел **«История и восстановление»** показывает локальные committed-транзакции, а не шаги браузерной кнопки «Отменить».

- Восстановление предыдущего состояния создаёт новую транзакцию; старая история не переписывается.
- Удаление записи создаёт восстановимую резервную версию.
- Исходные фотографии при удалении записи автоматически не удаляются.
- JSON-экспорт переносит данные, но не байты фотографий. Для полного аварийного восстановления нужны и JSON/source-файлы, и `public/uploads`, и локальная история.

Настройте регулярную зашифрованную резервную копию всей рабочей папки, включая скрытую `.admin-runtime`. Секрет `.env.admin.local` храните только в защищённом локальном backup-контуре.

### Регламент долгосрочной эксплуатации

- После каждого рабочего сеанса убедитесь, что нужные записи имеют статус «Сохранено на компьютере», а важные изменения либо опубликованы в preview, либо явно оставлены локальными.
- Не реже раза в неделю проверяйте завершение резервной копии; периодически выполняйте пробное восстановление в отдельную папку вместе с разработчиком.
- Перед сменой пароля сохраните или экспортируйте открытые черновики, затем полностью остановите админку: закройте окно launcher или нажмите в нём `Ctrl+C`. `update-password` и `rotate` откажутся менять файл, пока настроенный Admin API или любой другой процесс занимает его порт.
- При смене ответственного пользователя выполните `npm run admin:setup -- --update-password`. Новый пароль вступит в силу при следующем запуске админки; session secret при этой операции не меняется.
- При подозрении на компрометацию выполните `npm run admin:setup -- --rotate`. Команда разрешена только при остановленном launcher, меняет пароль и session secret; при следующем запуске сервер примет уже новый secret, поэтому все cookies, подписанные старым secret, будут недействительны.
- Обновления Node.js, npm dependencies, Astro и самой админки выполняет разработчик отдельным source release после полного QA. Не включайте автоматическое обновление рабочей папки без backup и rollback-плана.
- Не переключайте рабочий checkout на другую ветку: owner launcher привязан setup-проверкой к ожидаемой candidate-ветке.

## Фотографии и видео

Новые файлы сначала проходят проверку и временный staging. Они становятся постоянными только в одной транзакции вместе с сохранением записи; отменённая загрузка не должна оставлять бесхозный публичный файл.

Разрешены:

- изображения JPEG/JPG, PNG и WebP — до 10 МБ на файл;
- видео MP4 и WebM — до 90 МБ на файл.

Новые SVG, GIF, HEIC/HEIF, PDF, архивы и исполняемые файлы запрещены. Старые SVG могут встречаться в библиотеке как legacy-ресурсы, но загружать новые SVG нельзя.

При массовом выборе:

1. Проверьте очередь — файловый диалог операционной системы не гарантирует ожидаемый порядок.
2. Переставьте элементы стрелками, сортировкой или обратным порядком.
3. При необходимости отметьте обложку.
4. Подтвердите добавление в черновик.
5. Сохраните запись на компьютере.

Очередь обрабатывается максимум по два файла одновременно, а результат возвращается в порядке очереди, не в порядке завершения загрузки. За один выбор интерфейс принимает до 50 файлов.

## Импорт и экспорт JSON

- Экспорт одной записи, коллекции, page bundle или всего сайта не изменяет данные.
- Импорт всегда сначала строит preview/diff без записи.
- `merge` сохраняет отсутствующие во входном JSON поля; `replace` требует отдельного подтверждения.
- Массовый import не удаляет отсутствующие записи сам по себе.
- Apply создаёт одну локальную crash-recoverable транзакцию и не запускает публикацию.
- Full-site JSON не содержит сами фотографии; храните media backup отдельно.

Если preview показывает blocker или неожиданно большой список изменений, ничего не применяйте и передайте отчёт разработчику.

## Тестовая публикация

Публиковать можно только уже сохранённые committed-транзакции. Перед подтверждением админка показывает точный список сущностей и файлов.

После подтверждения система:

1. перепроверяет план и состояние веток;
2. создаёт prospective commit только из выбранных content/media paths;
3. запускает gates в отдельном чистом checkout именно на этом commit;
4. атомарно отправляет один и тот же проверенный SHA в `v4-product-final-candidate` и `preview`;
5. подтверждает успех только после GitHub workflow, GitHub Pages и live smoke для того же SHA.

Ветка `main` снимком проверяется до и после операции, но не обновляется. Последовательного fallback push нет: если atomic push недоступен или отклонён, публикация останавливается без попытки отправить ветки по одной.

Не нажимайте публикацию повторно, пока активная операция имеет статус «подготовка», «проверки», «в очереди» или «сборка». При неопределённом сетевом результате используйте восстановление/повтор из того же задания: система сначала сверяет обе remote-ветки и переиспользует тот же tested SHA.

## Если что-то пошло не так

- **«Не выполнен setup»** — запустите `npm run admin:setup` или позовите разработчика.
- **«Зависимости не установлены»** — разработчику нужно выполнить `npm ci`.
- **Порт занят** — закройте старое окно админки и запустите ярлык снова. Не меняйте порты наугад.
- **Сессия истекла** — войдите снова; браузерный черновик должен остаться доступным.
- **Конфликт revision** — не перезаписывайте файл вручную; используйте сравнение/merge или скачайте черновик.
- **Ошибка сохранения** — локальная запись не применена, черновик остаётся в браузере.
- **Ошибка публикации/build** — локальные сохранения не потеряны. Откройте отчёт, зафиксируйте `jobId` и tested SHA, передайте их разработчику.
- **Нет подтверждения exact SHA** — считайте тестовый сайт не обновлённым, даже если страница внешне открывается.

Не используйте ручной `git add`, `git commit`, `git push`, reset/clean или удаление runtime-файлов как «быстрое исправление». Техническое восстановление выполняется по [release runbook](deploy.md).

## Границы H6

- Local Save, история, import/export и preview publish реализованы.
- Preview предназначен для проверки и закрыт от индексации, но доступен по ссылке.
- Production-публикация и production admin backend не реализованы; это отдельный этап H7 с отдельным review безопасности и хостинга.
